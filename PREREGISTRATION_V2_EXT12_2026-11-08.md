Author: Syrym Zhakypbekov. Written in the night of 07/08.11.2026, Almaty (about 00:45, 08.11.2026 Almaty = 19:45 UTC 07.11.2026).
Addendum to PREREGISTRATION_V2_NETWORKS_2026-11-08.md (batch A, commit 4464e34) and PREREGISTRATION_V2_BATCHB_2026-11-08.md
(batch B). Everything not stated here is as in the batch-A plan.

## 1. Timing and what was known at the commit
- This addendum was written AFTER the batch-A runs had started on the compute fleet and BEFORE any batch-A or batch-B result was
  opened: no episode, association, availability, detection count or score of any batch-A or batch-B network was read, and the
  scorer (analysis/v2_networks.py) had not been run on any v2 data. Nothing under results/v2/runs/ and no v2_eval*.json was opened
  while writing it. What was known: the run lists (networks.json, networks_batchB.json) and the fleet deviation log
  (results/v2/FLEET_DEVIATIONS.md), which records only which networks failed tuning because their tuning week had no data.
- The reason for the extension is spare compute after batch B (the fleet would otherwise be idle after about 02:45 Almaty), not
  any outcome.
- Batch A and batch B are unchanged: networks.json and networks_batchB.json regenerated by the extended
  analysis/v2_finalize_networks.py are byte-identical to the pushed files (checked with cmp before this commit).

## 2. Networks
Every batch-A network that passed tuning, i.e. the 10 batch-A networks minus the three "not run" in FLEET_DEVIATIONS.md
(AF, AB, AW: a role with no data in the tuning week). Seven networks, in batch-A rule order:
OH (USA-Mexico), IV (Europe incl. Alps-Balkans), AU (New Zealand-SW Pacific), C1 (South America), AV (Alaska-Aleutians-Canada),
KR (Central Asia), JP (East Asia-West Pacific). Run ids <NET>_EXT12. The list is written by analysis/v2_finalize_networks.py (not
by hand) to results/v2/networks_ext12.json, in the networks.json format plus id, batch_A_rule_order, tune_end, thresholds,
output_dir and period_covered_by_selection_metadata. Stations, roles and sites are exactly those of batch A. Batch-B networks
are not extended.

## 3. Period, thresholds, rule, code
- Evaluation period: 2024-07-08 .. 2025-01-08 (exclusive; 184 days) = the six months immediately following the batch-A period
  2024-01-08 .. 2024-07-08. Batch A + ext12 = 2024-01-08 .. 2025-01-08 (366 days).
- Tuning: NO new tuning. The tuning week stays 2024-01-01 .. 2024-01-08 and the thresholds are the frozen per-role thresholds of
  that network's batch-A tuning run (status.json "thresholds" of the batch-A run, passed as P10_FIXED_THR). The runner must not
  derive a tuning week from the ext evaluation start (its default "7 days before evaluation start" does not apply here). Reading
  the thresholds is reading tuning-week values, not outcomes.
- Coverage by metadata: only JP passed the selection rule in window W2 (stream epochs cover 2024-01-08 .. 2025-01-08); the other
  six passed in W1, whose metadata window ends 2024-07-08, so the selection metadata did not check the ext period for them. This
  is stated now; their ext coverage is decided only from the processed availability and the exclusion rules below. No station
  is substituted.
- Rule v2 (sites with D = 50 km, site states, weights 0.25 / 0.20 / 0.15, SNR 0.40), every frozen parameter of section 3 of the
  batch-A plan, the frozen pipeline (pipeline/extended_stalta_criteria.py through pipeline/p10_v2_datacentre_wrapper.py outside
  EarthScope), quarterly chunks (2024-07-08 .. 2024-10-08, 2024-10-08 .. 2025-01-08), catalogue re-run rule of section 4.
- Outputs: results/v2/runs_ext12/<NET>/ (so that batch-A outputs under results/v2/runs/<NET>/ are never overwritten).
- Exclusion (ext period alone): unrecovered catalogue failure, fewer than 30 associated episodes in the ext period, or no data
  for the reference over the ext period: reported, not replaced.
- Scorer: analysis/v2_networks.py gets, in a separate logged commit before any ext output is scored, only a run-list/directory
  mode (EXT: networks_ext12.json, runs_ext12 -> results/v2/v2_eval_ext12.json; AEXT: batch-A and ext12 outputs of the same
  network concatenated by date -> results/v2/v2_eval_A_ext12.json). No computation changes; the merge unit tests must pass.

## 4. Hypotheses (identical to batch A)
**Primary of this addendum (ext period alone, pooled over the included ext12 networks).** V1 and co-primary V1r of the batch-A
plan: CG (rule v2) non-inferior to P3 7.5 dB, margin 3 pp on the upper 95 % bound of the pooled difference in dismissed share of
associated episodes; ratio (CG + 0.5) / (P3 + 0.5) upper 95 % bound <= 1.5. Two-stage cluster bootstrap (networks, then days
with episodes), 2000 resamples, seed 7. Secondary V2-V8 of the batch-A plan on the same pooled set, unchanged (V7 exercised
only with >= 10 associated episodes on outage days from >= 2 networks; V8 not exercised if no all-missing episode).
**Per network (secondary).** V1 per ext12 network with the day bootstrap; one-sided p = (draws >= 3 pp + 1)/(draws + 1); Holm
step-down across the included ext12 networks at one-sided alpha 0.025; unadjusted results also reported.
**Combined batch-A period + ext period (secondary).** For each network included in BOTH the batch-A analysis and the ext-alone
analysis: all its associated episodes of 2024-01-08 .. 2025-01-08 together; the same V1, V1r and V2-V8 pooled over these networks
(same bootstrap; days with episodes of both periods form one day set per network), and Holm per network across them. A network
included in only one of the two analyses is reported but not in the combined set.
The batch-A primary remains the batch-A primary and the batch-B primary remains the batch-B primary; ext12 replaces neither, and a
combined result is never reported instead of the separate ones. Equal-weight mean of per-network differences reported beside every
pooled difference (descriptive).

## 5. Chance-association control
As section 6 of the batch-A plan, unchanged (catalogue P arrivals shifted by uniform 1..7 days with random sign, 100 shifts,
seed 7, wrapped circularly), computed per network over the ext calendar span for the ext analysis and over the combined
366-day span for the combined analysis; same reporting and the same flag rule.

## 6. Compute order and stopping
- ext12 networks are queued AFTER batch B (after every batch-B network has started), in batch-A rule order (OH, IV, AU, C1, AV,
  KR, JP). The platform per network is logged in EXPERIMENT_LEDGER.md and does not change code or parameters.
- An ext12 network whose processing has not finished by 05:00 Almaty (00:00 UTC) on 08.11.2026 is reported as
  "not completed (compute)", with the chunks that finished described but not scored. It is never dropped silently and never
  replaced; its batch-A result is unaffected.
- No network is added, dropped or reordered after this commit. Analysis is run once per mode (EXT, AEXT) by the pushed scorer
  after every ext12 network has finished, been declared not run, or been declared not completed (compute). A scorer bug found
  later is fixed in a separate logged commit with before/after output kept.

## 7. Reported whatever the outcome
All ext12 and combined hypotheses are reported, including failures, non-exercised ones and networks not completed. No threshold,
weight, margin, D, network, order or period is changed after data are seen.
